# Hands-On: FreeRTOS with Live Variables & Live Watch

This hands-on exercise walks you through initializing a real-time multi-threaded environment using FreeRTOS on an STM32C5 microcontroller. You will learn how to handle hardware timebase conflicts, inspect active OS task runtime states, and monitor global variables in real-time without halting the processor using the VS Code Live Watch extension interface.

---

## ⚙️ 1. Hardware & OS Infrastructure Configuration (STM32CubeMX2)

1. Launch **STM32CubeMX2**, select **Start from MCU**, and search for the part number: `STM32C562RET6`.
2. Click **Automatically Download, Install & Create Project**.
3. In the Pinout search field, type `PA5`. Right-click pin **PA5** ➞ **Assign signal** ➞ **GPIO**.
4. Click the **Gear icon (Configure)** on the pin to modify parameters:
   * **SW Label for signal:** `LED1`
   * **Mode:** `Output`

### Resolving the SysTick Conflict
1. In the left peripheral menu, navigate to **Middlewares & Utilities ➞ FreeRTOS** and select **Activate**.
2. ⚠️ **Critical Architectural Warning:** Notice the configuration conflict warning thrown by the platform interface! Because the FreeRTOS kernel dynamically commandeers the system hardware `SysTick` timer to manage task scheduling and thread context slicing, it can no longer safely drive standard HAL timing loops.
3. To resolve this, open **Peripherals ➞ TIM6** and click **Activate**.
4. Now open **Project settings ➞ HAL common definitions ➞ HAL timebase selection**. 
5. Switch the selection from *SysTick* over to **Timer**, and explicitly assign **TIM6** from the drop-down menu.

### OS Task Setup & Generation
1. Navigate back to **FreeRTOS ➞ Applicative ➞ Tasks**. Observe the task management table.
2. Click **Add item to Tasks** to generate a custom thread entry slot. You can leave the generation parameters at their default values for this exercise.
3. Move to **Project settings** and verify that your toolchain output **Format** is explicitly set to **CMake**.
4. Click **Generate code** to export the project.

## 💻 2. Application Integration (VS Code)

1. Open your generated project folder within VS Code.
2. Respond **Yes** to the automatic system prompt: *"Configure discovered CMake project(s) as STM32Cube project(s)?"*.
3. Select the active toolchain build preset: `debug_GCC_STM32C562RET6`.
4. Run a baseline project compilation check by pressing **CTRL + Shift + B**.

### Establish a Source Code Baseline
Before inserting custom code blocks, establish a local clean checkpoint:
1. Open the **Source Control** tab on the left sidebar.
2. Click **Initialize Repository** to stage your pristine configuration state.

### Inspecting Generated OS Middleware
Navigate to `generated/middleware/mx_freertos_app.c` to examine the autogenerated code framework structure:
* Look at the top of the file to see the `function1` processing function prototype.
* Locate the task instantiation function blocks where the kernel memory stacks are registered.
* Scroll to the bottom of the file to view the empty placeholder code definition block for `function1`.

> ⚠️ **Platform Architecture Note:** The individual task wrapper functions generated within `mx_freertos_app.c` should ideally be declared using the `__weak` compiler attribute to allow clean clean overrides. This has been noted and reported as an environment feedback item.

### Stitching FreeRTOS into Main Execution
By default, the autogenerated code defines the OS assets but does not automatically invoke them during the standard microcontroller boot loop. If you search all files using **CTRL + Shift + F** for `app_synctasks_init`, you will find it is not called. We must manually launch it.

1. Open `main.c` and declare your middleware file dependency at the top of the file:
```c
/* Includes ------------------------------------------------------------------*/
#include "main.h"
#include "mx_freertos_app.h"
```

2. Scroll down to the `main()` function execution path. Find the code comment marker block indicating where custom user code loops can begin, and insert the synchronization initialization and kernel scheduler engine trigger functions right before the infinite `while(1)` block:

```c
    /*
     * You can start your application code here
     */
    app_synctasks_init();   // Initialize OS tasks and queues
    vTaskStartScheduler();  // Turn control over to the FreeRTOS Kernel

    while (1)
    {
        // Execution will never reach this point as the OS takes over
    }
}
```

### Implementing the Thread Action
1. Open `mx_freertos_app.c` and scroll down to the infinite loop context inside `function1`.
2. Declare a global tracking variable at the top of the file, and insert your non-blocking LED toggle task logic inside the runner loop:

```c
/* Private variables ---------------------------------------------------------*/
uint32_t Cnt = 0; // Global Variable for Real-time Profiling Tracking

static void function1(void *pvParameters)
{
  ( void ) pvParameters;

  for(;;)
  {
    HAL_GPIO_TogglePin(LED1_PORT, LED1_PIN);
    Cnt++; // Increment trace counter metrics
    vTaskDelay(200); // Efficient Non-blocking OS thread yield (200 ticks)
    
    /* Infinite loop executing LEDToggleTask functionality. */
  }
}
```

## 🔍 3. Advanced RTOS Debugging & Live Watch Setup

Managing real-time multi-threaded firmware requires specialized debugging features. We will update our configuration settings file to enable RTOS object tracking and variable sampling.

1. Navigate to the **Run and Debug** side panel view (**CTRL + Shift + D**) and click the configuration setup option link to generate a workspace `launch.json` file.
2. Choose **STM32Cube: Launch STLink GDB Server** as your target.
3. Open your generated `.vscode/launch.json` file and append the following parameters into the main configuration block array:

```json
"preBuild": "${command:st-stm32-ide-debug-launch.build}",
"runEntry": "main",
"serverRtos": {
    "enabled": true,
    "port": "60000",
    "driver": "freertos"
},
"liveWatch": {
    "enabled": true,
    "samplesPerSecond": "4"
}
```
> 💡 **Developer Note:** The integrated ST-Link GDB server architecture currently supports built-in thread-awareness drivers for both `freertos` and `threadx` environments. While setting these configurations up manually inside a JSON file is standard in VS Code across multiple programming ecosystems (such as Python or C++ development), a graphics-based UI helper utility option for configuring `launch.json` properties may be introduced in future extension updates.

## 📊 4. Testing & Real-Time Performance Profiling

1. Press **F5** to flash your target microcontroller hardware and launch a debug tracking session.
2. Look at the lower status bar panel options: a new specialized **STM32CUBE RTOS** tracking window monitor option pane will appear.
3. Click on **Open in Editor** within that tracking pane to display a live context table containing your OS task data stacks.
4. **Observation:** Notice that while your code runs uninterrupted, the `IDLE` daemon thread registers as `RUNNING`.
5. Now, place a hardware breakpoint marker directly onto the `HAL_GPIO_TogglePin()` line trace inside your `function1` block.
6. **Observation:** The execution instantly freezes! Look back at your task editor tracking data interface: your user thread (e.g., `LEDToggleTask`) now registers its operational state as `RUNNING`. Remove the breakpoint and hit **F5** to resume full execution speed.

### Monitoring Data with Live Watch
Traditional watch windows require you to halt the processor core to evaluate changes, destroying your real-time scheduling dynamics. The **Live Watch** interface uses background memory sampling buses to look at data values while the hardware is fully running.

1. Look at your left-hand explorer sidebar dashboard options panel to locate the specialized **STM32CUBE LIVE WATCH** panel interface.
2. Add your global parameter monitoring variable tracking name `Cnt` directly into the item input field layout.
3. **Observation:** Look at the variable value field. Because our `launch.json` profile specifies a continuous sample rate of 4 updates per second, you can observe the variable values dynamically incrementing in real-time while the onboard LED continues to blink smoothly!
4. For comparison, try adding the exact same variable parameter `Cnt` into the standard VS Code **Watch** panel. Notice that the standard window values will not update unless you manually pause the microcontroller execution core.

### Setting Up Conditional Breakpoints
If a counter variable increments thousands of times per second, a standard breakpoint is useless for tracking down specific runtime glitches. 

1. Locate the line trace file margin next to `Cnt++;` inside `mx_freertos_app.c`.
2. Right-click on the breakpoint margin area ➞ Select **Add Conditional Breakpoint**.
3. Type your targeted analytical check expression string into the text container: `Cnt == 20`.
4. **Observation:** Your hardware execution tracks through loop operations continuously without lagging, and will only freeze the processing core exactly when your monitoring expression match evaluates as true.
